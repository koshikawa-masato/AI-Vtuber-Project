# ローカルLevによる入口・外部検索直前のPII検査

## 実装した流れ

入力 → NFKC正規化・形式検査 → キーワードに応じたローカルLev判定 → 会話処理 → 検索リクエスト本文の組み立て → 本文全体の形式検査・ローカルLev判定 → 許可時のみ外部検索。

`privacy_guard`は通常の`JEV_PROVIDER`に関係なく、既定でローカルLevを使用する。クラウドのJevクライアントを渡された場合も送信せず保留する。Levはループバックの数値アドレスに限定し、HTTPプロキシ環境変数とリダイレクトを無効化する。クラウドのAPIキーは送らず、Lev障害時のクラウドへの切り替えも行わない。

判定確率は0.3以下で通過、0.7以上で検出、その間は保留。接続・設定エラーも保留。これらは暫定閾値であり、日本語での適切な校正を保証するものではない。

入口は既存のキーワード絞り込みを維持する。出口はキーワードの有無に関係なく文脈判定を行う。`ask_grok_with_search`で実際に送信するJSON本文を組み立ててから検査するため、プロンプト中の履歴や参考情報も検査対象になる。認証ヘッダーはモデルに渡さない。

現在のコードにあるxAI検索送信経路への実装であり、将来追加する別のWeb検索クライアントにも送信直前の`screen_outbound(payload)`が必要。LINE、会話生成、埋め込みなど全外部経路を一括ローカル化したものではない。

## 確認結果

| 確認内容 | 結果 |
|---|---|
| 自動テスト | 79件＋36サブテスト成功 |
| VPSの隔離ディレクトリとWSL2実機Levによるドライラン | 13ケースすべて期待一致 |
| 電話番号・全角メールアドレス | Levへ渡す前に遮断 |
| 健康情報／架空の病院ドラマ | 実機Levで遮断／通過 |
| 公開情報の検索 | 送信直前まで到達、HTTP送信はスタブで停止 |
| 履歴中の電話番号・収入情報 | 外部送信なし |
| 確率0.40・接続失敗の注入 | 保留、外部送信なし |
| 本番入力ハンドラーへの保留分岐追加 | 関数をサーバー内で抽出して検証、違反カウントなし |
| Levサーバーを実際に停止 | 入力保留、外部検索なし、クラウドへの代替接続なし |

実機モデル呼び出しは4回。通常判定は通信込みで約255〜315ms、初回は約2.01秒。合成ケースを1回ずつ通した動作確認であり、精度ベンチマークではない。障害・曖昧判定の一部は決定的な注入テスト。追加で実際にLevを停止した接続失敗も確認した。

本番PIDは2581411、ActiveState=active、NRestarts=0を維持。本番の稼働ファイルや設定は変更していない。検証用モデルとトンネルは終了する。既存本番トラフィックは従来構成のままである。

## 再実行

WSL2の専用環境でLevをループバックに起動し、VPS上ではループバックのSSHトンネルで接続する。初回取得後は`HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`を使える。VPSからWSL2への通信は残るため、「VPS内だけで完結」する構成ではない。

```sh
PYTHONDONTWRITEBYTECODE=1 python benchmarks/lev_privacy_dry_run.py
python -m pytest tests/test_privacy_guard.py tests/test_fact_check_pipeline.py tests/test_local_privacy_flow.py tests/test_jev_memory.py -q
```

設定例は`.env.lev.example`。全判定もLevへ切り替える場合は`JEV_PROVIDER=lev`を指定する。PII判定はその指定がなくてもローカルLevを使う。秘密情報を環境例へ記載しない。

## 本番反映時の差分

本番のWebhookは手元の版より進んでおり、既に違反カウント・削除依頼処理を含む。一式を上書きせず、添付の`lev_privacy_production_gate.patch`により、既存の`result.blocked`処理より先に`result.review_required`を扱う必要がある。保留を違反として加算しないための必須差分。

手元のWebhookには入口検査を追加済み。本番向けの保留分岐はサーバー内の本番関数から抽出したコピーで実行確認したが、稼働サービスにはまだ適用していない。コード一式のコピーは自動承認レビューで範囲過大として拒否されたため、必要なローカルモジュールだけを隔離環境へ送り、本番ハンドラーはサーバー内で関数のみ検証した。

確率や正規表現による見逃しはあり得る。キーワードを含まない入口の機微情報、文脈を分割した情報、同時リクエスト負荷の追加評価は別途必要。
